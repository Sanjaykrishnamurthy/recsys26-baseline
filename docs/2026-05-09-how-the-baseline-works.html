How the Baseline Works

A deep-dive into the music-crs-baselines system — how it retrieves relevant tracks from a large catalog and generates natural language responses in a multi-turn conversational music recommendation setting.

📅 Documented: 2026-05-09  ·  📦 Package: mcrs  ·  🐍 Python ≥ 3.8

1 The Two-Stage Pipeline

The baseline mimics how a human music expert would help you: first find relevant songs, then explain them naturally. These two jobs map to two distinct AI modules.

💬 User Input  —  "I want something chill and jazzy for a rainy evening" + full chat history from previous turns
↓
Stage 1 🔍 RecSys — Track Retrieval

Searches the entire track catalog (~100K+ songs) and returns the top-20 most relevant track IDs. Uses either BM25 (keyword-based) or BERT (semantic embedding).

→ Output: ["track_001", "track_045", "track_112", ...] (20 IDs)

↓ top-1 track → look up metadata in MusicCatalogDB
Stage 2 🤖 LLM — Response Generation

Feeds the system prompt, full chat history, and the top-1 track's metadata into Llama-3.2-1B-Instruct. Generates a natural language reply explaining the recommendation.

→ Output: "Here's a timeless pick — 'Blue in Green' by Miles Davis..."

↓
📄 Submission JSON  —  session_id, user_id, turn_number, predicted_track_ids (20), predicted_response
ℹ️

The top-20 track IDs are returned for RecSys evaluation (did a good track appear in the list?), while the natural language response is evaluated for NLU / dialogue quality. These are scored separately.

2 Stage 1A — BM25 Retrieval (Sparse)

BM25 is a classical text-search algorithm — think of it as a very smart search engine. It works by matching keywords in the user's query against a pre-built index of track metadata.

✅

Strengths

Fast, no GPU needed for retrieval. Works well when users name specific artists or songs.

⚠️

Weaknesses

Pure keyword matching — misses semantic meaning. "Chill evening vibe" won't match "ambient jazz" without shared words.

How the Index is Built

# mcrs/retrieval_modules/bm25.py — BM25_MODEL.build_index()

# Each track becomes a text document:
corpus = [
    "track_name: Blue in Green\nartist_name: Miles Davis\nalbum_name: Kind of Blue\n",
    "track_name: Autumn Leaves\nartist_name: Bill Evans\nalbum_name: Portrait in Jazz\n",
    # ... one entry per track in the catalog
]

corpus_tokens = bm25s.tokenize(corpus)
retriever = bm25s.BM25()
retriever.index(corpus_tokens)
retriever.save("./cache/bm25/track_name_artist_name_album_name")

How Retrieval Works

# At inference time:
query = "user: I want chill jazz\nassistant: Here's Blue in Green...\nuser: something with piano?"
query_tokens = bm25s.tokenize([query.lower()])
results = retriever.retrieve(query_tokens, k=20)
# → returns top-20 track IDs by BM25 score
💡

The index is cached to disk at ./cache/bm25/. If you change corpus_types in the config, delete the cache folder so it rebuilds: rm -rf cache

3 Stage 1B — BERT Retrieval (Dense)

BERT encodes both the query and every track as a 768-dimensional vector (a list of numbers representing meaning). Retrieval is done by finding the vectors most similar to the query vector — this understands semantics, not just keywords.

✅

Strengths

Understands meaning and context. "Chill rainy evening" can match "ambient jazz" even without shared words.

⚠️

Weaknesses

Slower to build index. Requires GPU for fast retrieval. bert-base-uncased is a relatively weak encoder.

How Retrieval Works

# mcrs/retrieval_modules/bert.py — BERT_MODEL

# Step 1: Encode query into a 768-dim vector
query_emb = mean_pool(bert_model(tokenize(query)))   # shape: [768]
query_emb = F.normalize(query_emb, p=2)            # L2 normalize

# Step 2: Cosine similarity against all pre-computed track embeddings
# (cached as embeddings.pt — shape: [num_tracks, 768])
scores = torch.matmul(embeddings, query_emb)         # [num_tracks]
top_indices = torch.topk(scores, k=20).indices

# Step 3: Map indices back to track IDs
track_ids = [all_track_ids[i] for i in top_indices]

4 What Goes Into the Index

The corpus_types config field controls which track metadata fields are included in the text that gets indexed. More fields = richer retrieval signal.

Field Example Value Default? Notes
track_name"Blue in Green"✅ YesCore identity of the track
artist_name"Miles Davis"✅ YesMost important for user queries
album_name"Kind of Blue"✅ YesProvides genre/era context
release_date"1959-08-17"✅ YesUseful for era-based queries
tag_list["jazz", "piano", "chill"]❌ NoAdd to config for mood/genre retrieval

Each track document fed to the index looks like this:

track_name: Blue in Green
artist_name: Miles Davis
album_name: Kind of Blue
release_date: 1959-08-17

5 Stage 2 — LLM Response Generation

The language model receives three inputs and generates one natural language response. Under the hood it is any HuggingFace causal LM — the default is Llama-3.2-1B-Instruct. 

# mcrs/lm_modules/llama.py — LLAMA_MODEL.response_generation()

# Build chat template:
chat_data = [
    {"role": "system",    "content": sys_prompt},    # role + rules + (optional) user profile
    {"role": "user",      "content": "I want chill jazz..."},
    {"role": "assistant", "content": recommend_item},   # top-1 track metadata → primes the LLM
]

# Apply tokenizer chat template + generate
inputs = tokenizer.apply_chat_template(chat_data, tokenize=False, add_generation_prompt=True)
outputs = model.generate(input_ids, max_new_tokens=512)
response = tokenizer.decode(outputs[input_ids.shape[1]:])   # only new tokens
🔑

The recommend_item string is injected as an assistant turn, not a user turn. This is the key trick: it primes the LLM to continue from that context, so it naturally explains and expands on the given track rather than generating a random response.

6 The System Prompt

The system prompt is assembled dynamically from three text files in mcrs/system_prompts/:

FileRoleAlways included?
roleplay.txtDefines the assistant persona ("You are an expert music recommendation assistant...")✅ Always
response_generation.txtFormatting rules — how to structure the recommendation response✅ Always
personalization.txtInjection template for user profile dataOnly if user_id is provided
 
# mcrs/crs_baseline.py — _get_system_prompt()

system_prompt = role_prompt["role_play"] + role_prompt["response_generation"]

if user_id:
    profile = user_db.id_to_profile_str(user_id)
    # → "user_id: 42\nage_group: 25-34\ngender: F\ncountry_name: South Korea"
    system_prompt += role_prompt["personalization"] + '\n' + profile

7 Multi-Turn Conversations

Every session contains exactly 8 turns. The inference scripts process all 8 turns for each session, with each turn's prediction being independent (using only history up to that point).

Turn 1 — history: empty
🧑 User: "I want chill jazz for a rainy evening"
🤖 Retrieval input: "user: I want chill jazz for a rainy evening"
Turn 2 — history: [turn 1]
🧑 User: "I like that, something with more piano?"
🤖 Retrieval input: "user: I want chill jazz...\nassistant: Here's Blue in Green...\nuser: something with more piano?"
Turns 3–8 — history grows with each turn
Retrieval sees the full conversation as one text block — so later turns benefit from all prior context, enabling progressive preference refinement.
⚠️

Every submission file must contain predictions for all 8 turns of every session. Missing turns will cause evaluation errors. The inference scripts handle this automatically via for target_turn_number in range(1, 9).

8 Output JSON Format

Each turn produces one record. The final file is a JSON array of these records:

[
  {
    "session_id": "sess_abc123",         // unique session identifier
    "user_id": "user_42",            // user for personalization
    "turn_number": 3,               // integer 1–8
    "predicted_track_ids": [        // top-20 for RecSys eval
      "track_001", "track_045", ...
    ],
    "predicted_response": "Here's a wonderful pick..." // LLM output for NLU eval
  },
  // ... one object per turn per session
]
FieldTypeRequiredNotes
session_idstring✅Must match the dataset
user_idstring✅Must match the dataset
turn_numberint✅1 through 8 inclusive
predicted_track_idslist[str]✅Exactly 20 IDs for full credit
predicted_responsestring✅Can be "" for retrieval-only runs

9 How to Improve the Baseline

The baseline is intentionally simple. Here are the highest-impact directions to explore:

ImprovementDifficultyWhereExpected Impact
Add tag_list to corpus_types Easy Config YAML only Better mood/genre retrieval
Swap BM25 → BERT retrieval Easy Config YAML only Semantic query understanding
Swap Llama-1B → Qwen-4B Easy Config YAML only Richer, more coherent responses
Use E5/BGE instead of bert-base Medium bert.py model_name param Much stronger dense retrieval
Add an LLM reranker after retrieval Medium crs_baseline.py pipeline Better top-1 selection for LLM
Embedding-based personalized reranking Medium New reranker module User-specific track ordering
Generative retrieval with semantic IDs Hard Full new module + fine-tuning End-to-end unified architecture
